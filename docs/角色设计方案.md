# 角色设计方案

## 概述

系统共设计 **7 个角色**，由两个模型分别扮演。角色之间通过 LangGraph 工作流编排，形成"出题 → 解题 → 验证"的完整数据合成流水线。

---

## 一、角色总览

| # | 角色 | 扮演模型 | Temperature | Max Tokens | 核心职责 |
|---|------|---------|-------------|------------|----------|
| 1 | 提议者 (Proposer) | qwen3.7-max | 0.8 | 2048 | 出题 + 标准答案 |
| 2 | 正样本求解者 (Positive Solver) | qwen3.7-max | 0.2 | 4096 | 正确分步推理 |
| 3 | 负样本求解者 (Negative Solver) | qwen3.7-max | 0.7 | 4096 | 注入错误的推理 |
| 4 | 正样本验证者 (Positive Validator) | qwen3.7-max | 0.05 | 1024 | 正样本正确性判定 |
| 5 | 负样本验证者 (Negative Validator) | qwen3.7-max | 0.05 | 1024 | 负样本质量评估 |
| 6 | 策略模型采样器 (Strategy Sampler) | **qwen3-8b** | 0.7 | 4096 | 自然推理采样 |
| 7 | 策略样本验证者 (Strategy Validator) | qwen3.7-max | 0.05 | 1024 | 8B 样本正负标注 |

---

## 二、各角色详细设计

### 角色 1：提议者 (ProposerAgent)

```
┌─────────────────────────────────────────┐
│  提议者 Proposer                        │
│  ──────────────────────────────────     │
│  模型: qwen3.7-max                       │
│  Temp: 0.8 (高，需要问题多样性)           │
│  Max Tokens: 2048                        │
│  Prompt: proposer_system/user_prompt     │
│                                         │
│  输入 → 输出                             │
│  ────────────                            │
│  financial_data (JSON)                  │
│  task_type (评估维度)                    │
│  difficulty (0.1~1.0 随机)              │
│      ↓                                  │
│  · 分析问题 (question)                   │
│  · 标准答案 (answer/conclusion)          │
│  · 标准分析过程 (3+步骤)                  │
└─────────────────────────────────────────┘
```

**设计特点：**

- **难度感知**：Prompt 中包含难度等级说明，引导模型生成匹配难度的问题
  - 0.1~0.3：单一指标分析、基础财务比率计算
  - 0.4~0.6：多指标综合分析、趋势判断
  - 0.7~0.9：深度风险识别、跨期分析、异常诊断
  - 0.9~1.0：复杂综合评估、预警信号识别、决策建议
- **独立出题**：每个问题独立生成，不依赖历史问答对，避免难度偏差累积
- **高温设置 (0.8)**：确保问题的多样性和创造性，避免重复出题模式
- **双重产出**：同时产出问题 + 标准答案，标准答案是后续所有验证的基准

**为什么用 235B 而不是 8B？**
出题需要深度理解财务数据结构和业务场景，小模型难以生成有业务价值的高质量问题。

### 角色 2：正样本求解者 (SolverAgent.solve)

```
┌─────────────────────────────────────────┐
│  正样本求解者 Positive Solver            │
│  ──────────────────────────────────     │
│  模型: qwen3.7-max                       │
│  Temp: 0.2 (低，需要稳定准确性)           │
│  Max Tokens: 4096                        │
│  Prompt: solver_system/user_prompt       │
│                                         │
│  输入 → 输出                             │
│  ────────────                            │
│  question (提议者生成的问题)              │
│  financial_data (JSON)                  │
│      ↓                                  │
│  · 正确的分步推理 (analysis_process)     │
│  · 正确的分析结论 (conclusion)           │
└─────────────────────────────────────────┘
```

**设计特点：**

- **低温设置 (0.2)**：确保推理稳定、准确，减少随机性导致的不一致
- **无错误注入**：使用纯净的正样本 Prompt，没有任何"犯错"指令
- **独立解题**：不参考标准答案，仅基于问题 + 财务数据独立推理
- **分步推理**：要求输出至少 3 个分析步骤，每步有逻辑 + 数据支撑
- **专业框架**：遵循偿债能力/现金流/盈利能力/运营效率/结构性风险分析框架

**设计意图：**
提供"教科书级"的正确推理范例，作为 PRM 训练的正例。低温确保质量，但也意味着多样性有限——这正是为什么还需要 8B 的自然采样。

---

### 角色 3：负样本求解者 (SolverAgent.solve_negative)

```
┌─────────────────────────────────────────┐
│  负样本求解者 Negative Solver            │
│  ──────────────────────────────────     │
│  模型: qwen3.7-max                       │
│  Temp: 0.7 (中高，需要错误多样性)         │
│  Max Tokens: 4096                        │
│  Prompt: negative_solver_system/user     │
│         _prompt (含7类错误注入指令)       │
│                                         │
│  输入 → 输出                             │
│  ────────────                            │
│  question (提议者生成的问题)              │
│  financial_data (JSON)                  │
│      ↓                                  │
│  · 含迷惑性错误的分步推理                 │
│  · 与标准答案有偏差的结论                 │
│                                         │
│  可注入的7类错误:                         │
│  ① 计算错误  ② 公式引用错误               │
│  ③ 指标理解错误 ④ 逻辑跳跃                │
│  ⑤ 因果倒置  ⑥ 数据误读                  │
│  ⑦ 趋势误判                             │
└─────────────────────────────────────────┘
```

**设计特点：**

- **中高温设置 (0.7)**：促进错误类型的多样化，每次注入不同组合的错误
- **7 类错误体系**：覆盖财务分析中最常见的推理错误模式
- **自然迷惑性**：错误融入推理链中，不看结论对比难以察觉——这是一份"有缺陷的专业报告"
- **非全盘错误**：分析要在某些方面正确、关键点上出错，而非完全乱写
- **不标注错误类型**：模型输出不指明使用了哪种错误，保持自然

**设计意图：**
提供"高质量反例"——不是随机的错误答案，而是有专业外衣的、类似真实分析师可能犯的错误。这在 PRM 训练中帮助模型学习辨别"看起来对但实际错"的推理。

### 角色 4：正样本验证者 (ValidatorAgent.validate with is_positive_sample=True)

```
┌─────────────────────────────────────────┐
│  正样本验证者 Positive Validator         │
│  ──────────────────────────────────     │
│  模型: qwen3.7-max                       │
│  Temp: 0.05 (极低，评判需高度一致)        │
│  Max Tokens: 1024                        │
│  Prompt: validator_system/user_prompt    │
│                                         │
│  输入 → 输出                             │
│  ────────────                            │
│  question (原始问题)                      │
│  reference_answer (标准答案)             │
│  predicted_answer (正样本求解者答案)      │
│      ↓                                  │
│  · is_valid (true/false)                │
│  · similarity_score (0.0~1.0)           │
│  · reason (详细验证理由)                 │
└─────────────────────────────────────────┘
```

**设计特点：**

- **极低温 (0.05)**：验证必须稳定、一致，不能同一对答案给出不同判断
- **语义等价判断**：不要求字面一致，允许表述方式、步骤数量、侧重点的差异
- **多维度评估**：核心结论一致性、推理逻辑正确性、数据准确性、完整性、专业性
- **通过阈值**：similarity_score >= VALIDATION_THRESHOLD (0.8) 判定为通过

**设计意图：**
充当质量过滤器，确保只有真正正确的正样本才能进入训练集。

---

### 角色 5：负样本验证者 (ValidatorAgent.validate with is_positive_sample=False)

```
┌─────────────────────────────────────────┐
│  负样本验证者 Negative Validator         │
│  ──────────────────────────────────     │
│  模型: qwen3.7-max                       │
│  Temp: 0.05 (极低)                       │
│  Max Tokens: 1024                        │
│  Prompt: negative_validator_system/user  │
│         _prompt                         │
│                                         │
│  输入 → 输出                             │
│  ────────────                            │
│  question (原始问题)                      │
│  reference_answer (标准答案)             │
│  predicted_answer (负样本求解者答案)      │
│      ↓                                  │
│  · is_valid (true=有效负样本)            │
│  · similarity_score (0.0~1.0)           │
│  · reason (差异分析和质量评价)            │
└─────────────────────────────────────────┘
```

**设计特点：**

- **反向验证逻辑**：不同于正样本验证！
  - `is_valid = true`：预测答案与标准答案存在**实质性差异** → 误差注入成功 → 有效负样本
  - `is_valid = false`：预测答案与标准答案**高度一致**（错误注入失败）或**完全脱离常识**（缺乏迷惑性）
- **质量三维度**：实质性差异 + 错误自然度 + 专业迷惑性
- **排除两种情况**：
  - 错误注入失败（与标准答案太像）→ 无效
  - 完全胡说八道（缺乏专业迷惑性）→ 无效

**设计意图：**
确保负样本的质量——要的是"看起来像真的但实际有问题的推理"，而不是"明显错误的答案"或"没注入错误的正确答案"。

---

### 角色 6：策略模型采样器 (StrategyModelSampler)

```
┌─────────────────────────────────────────┐
│  策略模型采样器 Strategy Sampler         │
│  ──────────────────────────────────     │
│  模型: qwen3-8b ← 唯一用小模型的角色     │
│  Temp: 0.7 (模拟自然推理多样性)           │
│  Max Tokens: 4096                        │
│  Prompt: sampling_system/user_prompt     │
│  enable_thinking: False                  │
│                                         │
│  输入 → 输出                             │
│  ────────────                            │
│  question (提议者生成的问题)              │
│  financial_data (JSON)                  │
│      ↓ (每个问题执行3次)                  │
│  · 自然推理过程 (analysis_process)       │
│  · 自然推理结论 (conclusion)             │
│                                         │
│  可能对 → 后续标注为正样本                │
│  可能错 → 后续标注为负样本                │
└─────────────────────────────────────────┘
```

**设计特点：**

- **纯推理 Prompt**：去掉了所有"错误注入"、"专业要求"等引导，只要求"请分析以下财务问题"
- **无引导 = 最真实**：不给任何暗示要做对还是做错，让模型以最自然的状态推理
- **多次采样 (3 次)**：同一问题采样 3 次，获取不同的推理路径和结果
- **enable_thinking=False**：禁用 qwen3-8b 的思考模式，获得最直接的推理输出
- **温度 0.7**：保持一定的随机性，模拟真实推理时的自然多样性

**设计意图（核心价值）：**

这是整个系统中最关键的设计。qwen3-8b 作为"策略模型"（即实际生产环境中使用的小模型），它的自然推理输出具有最高价值：

1. **做对了** → 这是 8B 模型能力边界内的真实正样本
2. **做错了** → 这是 8B 模型真实的推理弱点，直接暴露了它在财务推理上的短板

与 235B 刻意构造的负样本不同，这些错误更真实、更多样、更贴近实际部署时遇到的问题。用这些数据训练 PRM，能让 PRM 学会识别小模型在真实场景下的推理错误。

### 角色 7：策略样本验证者 (ValidatorAgent.validate_strategy_sample)

```
┌─────────────────────────────────────────┐
│  策略样本验证者 Strategy Validator        │
│  ──────────────────────────────────     │
│  模型: qwen3.7-max                       │
│  Temp: 0.05 (极低，标注需一致)            │
│  Max Tokens: 1024                        │
│  Prompt: sampling_validator_system/user  │
│         _prompt                         │
│                                         │
│  输入 → 输出                             │
│  ────────────                            │
│  question (原始问题)                      │
│  reference_answer (235B标准答案)         │
│  predicted_answer (8B推理答案)           │
│      ↓                                  │
│  · is_valid (true=8B做对了, 标注为正样本) │
│  · similarity_score (0.0~1.0)           │
│  · reason (标注依据)                     │
└─────────────────────────────────────────┘
```

**设计特点：**

- **简单的二元标注**：只判断 8B 的输出是否正确（vs 标准答案），不做复杂评判
- **极低温 (0.05)**：标注必须一致可靠
- **独立标准**：与正/负样本验证者使用不同的 Prompt，专注于"标注"而非"验证"
- **对错都收**：is_valid=true → 正样本；is_valid=false → 这才是最宝贵的负样本

**设计意图：**
235B 作为"老师"，批改 8B "学生"的作业。8B 做对了说明这个能力它已经具备，做错了说明这是它的真实弱点。

## 三、温度设计总结

```
Temperature 轴
    1.0 ┤
        │
    0.8 ┤  ● 提议者 (需要问题多样性)
        │
    0.7 ┤  ● 负样本求解者 (需要错误多样性)
        │  ● 策略模型采样 (需要自然多样性)
        │
    0.6 ┤
        │
    0.5 ┤
        │
    0.4 ┤
        │
    0.3 ┤
        │
    0.2 ┤  ● 正样本求解者 (需要准确稳定)
        │
    0.1 ┤
        │
    0.0 ┤  ● 正样本验证者 (评判需高度一致)
        │  ● 负样本验证者 (评判需高度一致)
        │  ● 策略样本验证者 (标注需高度一致)
        └──────────────────────────────────────
```

**温度设计原则：**

| 任务类型 | 温度范围 | 原则 |
|----------|---------|------|
| 创意生成（出题） | 0.7~0.9 | 需要多样性，避免模式重复 |
| 正确答案生成 | 0.1~0.3 | 需要稳定、准确，减少随机性 |
| 错误注入 | 0.6~0.8 | 需要错误类型多样化 |
| 自然采样 | 0.6~0.8 | 模拟真实推理多样性 |
| 评判/标注 | 0.0~0.1 | 需要高度一致，避免评判标准漂移 |

## 四、Prompt 设计对比

### 核心差异：引导 vs 无引导

```
qwen3.7-max 正样本求解 Prompt:
┌──────────────────────────────────────┐
│ "你是一位资深的金融分析师..."          │
│ 分析框架: 偿债能力、现金流...          │
│ 推理要求: 清晰步骤、数据支撑...         │
│ → 引导模型做正确的专业推理             │
└──────────────────────────────────────┘

qwen3.7-max 负样本求解 Prompt:
┌──────────────────────────────────────┐
│ "你是一位资深的金融分析师..."          │
│ 分析框架: 偿债能力、现金流...          │
│ 【特殊任务指令 - 错误注入】            │
│ 7类错误: 计算错误、公式引用错误...      │
│ 要求: 自然、合理、有迷惑性              │
│ → 引导模型在专业外衣下犯错误            │
└──────────────────────────────────────┘

qwen3-8b 采样 Prompt:
┌──────────────────────────────────────┐
│ "你是一位金融分析师，                  │
│  请基于提供的财务数据，                 │
│  对给定问题进行分步推理分析。"           │
│ 要求: 展示完整推理过程                  │
│                                       │
│ → 无引导！不暗示对错！自然推理！        │
└──────────────────────────────────────┘
```

**三个 Prompt 的差异是刻意设计的：**
- 235B 正样本 Prompt：最大化正确的可能性
- 235B 负样本 Prompt：引导产生特定类型的错误
- 8B 采样 Prompt：完全无引导，暴露模型的"裸"推理能力

---

## 五、为什么这样分配角色？

| 问题 | 回答 |
|------|------|
| 为什么出题用 235B？ | 需要理解财务数据结构，设计有业务价值的问题，8B 能力不足 |
| 为什么正样本用 235B？ | 标准答案需要高准确性，低温下的 235B 是最佳选择 |
| 为什么负样本用 235B？ | 刻意构造错误需要"知道正确答案然后偏离"，需要强模型能力 |
| 为什么 8B 只采样？ | 8B 的价值恰在其不完美——它的真实错误是最好的训练数据 |
| 为什么验证用 235B？ | 评判是复杂的对比推理任务，需要大模型的判别力 |
| 为什么不用 8B 做任何"智能"工作？ | 8B 在复杂推理任务上不够可靠，用它验证会引入噪声 |

## 六、数据流中的角色协作

```
                   ┌──────────┐
                   │ 财务数据  │ (JSON)
                   └────┬─────┘
                        │
                ┌───────▼───────┐
                │  ① 提议者      │ "这家公司的偿债能力如何？"
                │  标准答案出炉   │ "流动比率1.5，处于健康水平..."
                └───────┬───────┘
                        │ 同一问题分发给3个角色
          ┌─────────────┼─────────────┐
          │             │             │
    ┌─────▼─────┐ ┌─────▼─────┐ ┌─────▼─────┐
    │② 正样本    │ │③ 负样本    │ │④ 策略采样  │
    │235B 解题   │ │235B 解题   │ │8B 解题×3  │
    │Temp 0.2   │ │Temp 0.7   │ │Temp 0.7   │
    │做对        │ │故意做错    │ │自然推理    │
    └─────┬─────┘ └─────┬─────┘ └─────┬─────┘
          │             │             │
    ┌─────▼─────┐ ┌─────▼─────┐ ┌─────▼─────┐
    │⑤ 正验证    │ │⑥ 负验证    │ │⑦ 策略验证  │
    │vs 标准答案 │ │vs 标准答案 │ │vs 标准答案 │
    │对/错      │ │有效/无效   │ │正/负标注   │
    └─────┬─────┘ └─────┬─────┘ └─────┬─────┘
          │             │             │
          └─────────────┼─────────────┘
                        │
                ┌───────▼───────┐
                │  ⑧ Question   │
                │  SampleSet    │
                │  1标准+1正+1负 │
                │  +3策略 = 6条  │
                └───────────────┘
```
